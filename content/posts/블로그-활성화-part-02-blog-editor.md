블로그 운영을 자동화하고 편리하게 콘텐츠를 작성하기 위해 개발한 자체 호스팅형 'Blog Editor'의 개발 내역과 기술 스택을 정리한다. 외부 프레임워크나 무거운 서드파티 라이브러리 의존성 없이, 순수 Python 표준 라이브러리와 Vanilla JS만으로 구현하는 것을 원칙으로 삼았다.

## 1. 아키텍처 및 기술 스택 개요

- **Backend**: Python 표준 라이브러리만을 사용한 `server.py` (약 1,200라인). `http.server`, `subprocess`, `json`, `urllib.request` 등을 활용하며, Flask나 FastAPI, Requests 등 외부 패키지는 배제했다.
- **Frontend**: 빌드 도구나 프레임워크 없이 브라우저가 직접 실행하는 Vanilla JS, HTML, CSS (`app.js` 약 1,500라인).
- **독립된 저장소**: 블로그 코드와 에디터 코드가 완전히 분리된 구조다. 에디터의 소스 코드와 API 키 등 보안에 민감한 정보가 퍼블릭 블로그 저장소에 노출되지 않도록 설계했다.

UI는 데스크톱 환경에 맞추어 왼쪽 사이드바(목록 및 필터), 중앙 에디터 폼, 오른쪽 실시간 미리보기/디프(diff) 영역으로 이루어진 3단 고정 레이아웃이다.

## 2. 백엔드 구현 상세

### 프레임워크 없는 라우팅 및 콘텐츠 파싱
`server.py`는 단일 `http.server.ThreadingHTTPServer` 인스턴스로 구동된다. 별도의 라우팅 라이브러리 없이 `Handler` 클래스 내에서 정규식(`re.match()`) 분기만을 이용해 요청을 처리한다.

```python
# 라우팅 구현 방식 예시
if self.path == '/api/posts':
    self.handle_get_posts()
elif re.match(r'^/api/posts/(post|project)/(.+)/reset$', self.path):
    self.handle_reset_post(matched_groups)
```

마크다운 파일의 YAML Frontmatter 역시 서드파티 YAML 파서 없이 정규식과 라인 스플리터를 이용해 직접 파싱하도록 구현했다. 규격이 고정되어 있어 단순한 헬퍼 함수(`parse_frontmatter()`, `build_frontmatter()`)만으로 충분히 대응 가능하다.

### 상태 관리를 위한 최소한의 데이터베이스 구성
가벼운 에디터 구동을 위해 SQLite조차 도입하지 않고, gitignore 처리된 미니 JSON 파일들로 상태를 유지한다.

1. **`pending_deletes.json`**: 삭제 대기 파일 목록. 에디터에서 포스트를 삭제해도 즉시 파일을 unlink하지 않고 이 목록에 등록한다. 실제로 배포(`deploy()`) 명령이 내려지는 시점에 `unlink()`가 일어난다. 이미 배포된 적이 없는 신규 드래프트는 `git show HEAD:<path>` 조회를 통해 존재 여부를 파악한 뒤 배포 단계 없이 즉시 삭제 처리된다.
2. **`duplicate_links.json`**: 포스트 복제 시 발생하는 원본-복제본 연결 정보. 복제본 포스트는 작성일에 의해 상단으로 흩어지지 않고, 이 연결 관계에 의해 사이드바에서 원본 바로 위에 고정 배치된다. 복제본을 수정하고 저장하면 연결 정보는 자동 해제된다.
3. **`config.json`**: 외부로 유출되면 안 되는 Gemini API Key 등을 저장한다.

## 3. Gemini API 연동 및 AI 자동화

`call_gemini(prompt, schema)` 함수를 통해 구글 Gemini API에 원시 HTTP 요청을 전송한다. `generationConfig.responseSchema`를 활용하여 자유 텍스트가 아닌 사전에 정의한 JSON 스키마 규격대로만 응답받도록 구현했다.

### API 쿼터 고갈 대응 및 폴백 메커니즘
API 요청 중 429(Too Many Requests) 에러를 감지하면, 하위 모델 계열로 순차 전환하며 재시도하는 예외 처리를 적용했다.

```python
MODELS = ['gemini-3.5-flash', 'gemini-3.5-flash-lite', 'gemini-2.0-flash', 'gemini-2.0-flash-lite']
```
각 모델 계열은 독립적인 무료 프리 티어 쿼터를 사용하므로, 일시적인 사용량 고갈에 유연하게 대응할 수 있다.

### AI 드래프트 및 문장 다듬기 기능
- **AI Draft**: 지정한 특정 폴더 내부 및 상하위 디렉토리를 탐색하여 `info4blog.md` 텍스트 파일들을 찾아 병합하고 이를 기반으로 블로그 포스트(제목, 설명, 태그, 본문)를 생성한다. 이미지 파일은 임시 경로인 `/image/블로그-활성화-part-02-blog-editor/<filename>` 플레이스홀더를 사용하여 본문에 배치한 뒤, 최종 생성된 타이틀을 기준으로 슬러그가 결정되면 해당 슬러그 디렉토리 경로로 일괄 문자열 치환하도록 코딩하여 모델이 슬러그를 직접 추측할 필요가 없도록 만들었다.
- **AI Polish**: 작성 중인 본문에 피드백이나 지시사항을 반영하여 다시 작성해 준다. 백엔드에서 단순히 텍스트만 덮어쓰는 것이 아니라, 변경 사항을 프론트엔드에서 수락/거절할 수 있는 차이점 뷰를 제공한다.

기존 프롬프트 템플릿 마크업으로 가볍게 마크다운 구분자(`---`)를 사용하자 모델이 이를 실제 출력 결과물에 포함하는 이슈가 있어, 확실히 구분 가능한 `<<<START>>>` / `<<<END>>>` 태그 형태로 포맷을 개정하여 안정성을 높였다.

## 4. 프론트엔드 구현 및 고유 기능

### Word-level LCS 기반의 부분 병합 뷰
외부 디프 라이브러리를 쓰지 않고, 순수 자바스크립트로 단어 단위 LCS(최장 공통 부분 수열) 정렬 알고리즘을 구현했다. 생성된 헌크(Hunk) 단위로 변경점을 모아 사용자가 클릭하는 방식으로 수정 제안을 부분 수락하거나 거절할 수 있다.

[ AI Polish의 차이점 비교(diff) 및 수락/거절 화면 사진 ]

### 팝오버(Popover) 대 모달(Modal) 설계 정책
- **Popover**: 태그 선택기, 이미지 관리자, 매뉴얼/AI 초안 선택 창처럼 특정 버튼 주위에 밀착해 열리고 외부 클릭 시 바로 닫히는 가벼운 액션에 적용했다.
- **Modal**: 배포 승인 디프 창, 전체 삭제 확인 창, AI 생성 마법사 등 넓은 영역에서 신중하게 결정을 내려야 하는 요소에 한해 화면 뒤편에 어두운 오버레이를 까는 형태로 격리 설계했다.

[ AI Draft 폴더 브라우저 및 옵션 선택 화면 사진 ]

### CSS 변수를 통한 단일 테마 컨트롤
테마는 단 한 줄의 CSS 커스텀 프로퍼티 수정을 통해 일괄 조정된다. 기본 테마 컬러로 차분한 틸그린(Teal-Green) 계열을 설정했다.

```css
:root {
  --accent: #14b8a6; /* 메인 테마 컬러 */
}
```
수정 중인 드래프트는 주황색으로, 삭제 대기 항목은 붉은색, 추가 사항 및 활성화 상태는 녹색으로 시각화하여 사용자가 실수할 여지를 대폭 줄였다.

### Hugo 개발 서버 제어 제약 사항 해결
에디터 내에 라이브 미리보기를 출력하기 위해 `subprocess.Popen`으로 `hugo server`를 구동할 때, 휴고 서버가 인메모리가 아닌 `.preview/` 디스크 경로에서 페이지를 서빙하도록 설계했다. 이로 인해 임시 폴더가 직접 지워지면 프로세스는 정상이지만 404 에러가 나는 버그를 방지하기 위해 로깅 시스템을 부착했다. 또한 세션이 길어짐에 따라 생기는 싱크 밀림을 수동으로 잡을 수 있도록, 휴고 서브프로세스만 가볍게 재부팅시키는 재시작 API(`api/restart-preview`)를 별도로 배치했다.
