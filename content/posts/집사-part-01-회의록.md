# defib-secretary (집사) 개발 일지 및 아키텍처 분석

이 프로젝트는 디스코드 음성 채널에서 진행되는 회의를 실시간으로 녹음하고, Google Gemini API를 활용해 요약한 뒤, 그 결과를 Notion 페이지에 자동으로 기록하는 사내 비서 봇이다. Node.js 22와 discord.js 14를 기반으로 작동하는 단일 프로세스 애플리케이션이며, Docker 컨테이너 환경에서 실행된다.

이 글에서는 '집사' 봇의 전체 아키텍처, 핵심 파이프라인, 그리고 개발 과정에서 마주한 다양한 기술적 이슈들의 해결 과정을 상세히 정리한다.

## 1. 시스템 아키텍처 및 디렉터리 구조

전체 코드베이스는 다음과 같은 단일 프로세스 구조로 설계되었다.

- **`index.js`**: 애플리케이션의 진입점이다. 디스코드 이벤트를 바인딩하고 버튼 및 셀렉트 메뉴의 인터랙션을 핸들링하며, 세그먼트 회전 타이머와 임시 파일을 관리한다.
- **`src/session.js`**: 프로세스 전역에서 단 하나만 존재하는 세션 상태를 관리한다. 현재 상태를 정의하는 `STATES` 열거형, 중복 클릭 방지 락(lock), 재작성 히스토리 데이터를 보관하며 이를 `tmp/session-history.json` 파일에 저장해 영속화한다.
- **`src/ui.js`**: 디스코드 채팅창에 노출할 임베드 메시지, 제어 버튼, 드롭다운 셀렉트 메뉴를 구성하는 UI 빌더 모듈이다.
- **`src/audio.service.js`**: 음성 채널 연결 수립, Opus 오디오 스트림 구독 및 디코딩, PCM 파일 병합, ffmpeg을 이용한 MP3 변환 및 오디오 세그먼트 제어를 담당한다.
- **`src/gemini.service.js`**: 녹음 완료된 오디오 파일을 Gemini File API로 업로드하고 요약 텍스트를 생성한다. 호출 실패 시 백오프 재시도 및 모델 대체(Fallback) 로직이 포함되어 있다.
- **`src/notion.service.js`**: 노션 API를 사용하여 새로운 회의록 페이지를 생성하고, 생성된 요약문을 노션 블록 구조로 변환하여 페이지 본문에 추가(append)한다.
- **`src/time.util.js`**: 실행 환경의 시스템 타임존 설정에 영항을 받지 않고 항상 KST(한국 표준시)를 기준으로 날짜와 시각을 포맷팅한다.

## 2. 사용자 플로우 및 핵심 동작 매커니즘

### 인터랙션 제어
디스코드 채팅창에 `집사~` 명령어를 입력하면 봇이 제어용 임베드와 버튼 메뉴를 전송한다. 인터랙션 시 기존에 봇이 보냈던 제어 메시지는 자동으로 삭제되어 화면이 복잡해지는 것을 방지한다. 이때 봇 자신의 메시지만을 골라 지우기 때문에 디스코드 채널의 '메시지 관리(Manage Messages)' 권한이 별도로 요구되지 않는다.

### 회의 시작 및 메타데이터 동기화
사용자가 **회의 시작** 버튼을 누르면 봇이 해당 사용자가 참여 중인 음성 채널로 진입하여 녹음을 시작한다. 동시에 노션에 새로운 회의록 페이지가 생성된다. 이때 음성 채널 내 참석자들의 디스코드 역할을 수집한 뒤, 사전에 지정된 역할(`개발`, `기획`, `아트`)과 일치하는 항목만 노션의 **부서** 속성(Multi-select)에 자동으로 기입한다.

### 세그먼트 분할 및 자동 회전
회의 내용은 하나의 긴 오디오 파일이 아니라 **안건(Segment)** 단위로 분할되어 기록된다.
- **쉬는 시간**: 현재까지 수집된 녹음 데이터를 하나의 안건으로 마감한 뒤 Gemini 요약을 거쳐 노션 페이지에 추가한다. 음성 연결은 유지하되 오디오 캡처만 일시 정지한다.
- **회의 재개**: 새로운 안건 번호를 부여하고 오디오 녹음을 다시 시작한다.
- **자동 세그먼트 회전**: 사용자의 조작이 없더라도 백그라운드 타이머가 작동하여 일정 시간(기본 45분, `.env` 내 `SEGMENT_DURATION_MINUTES`로 지정)이 흐르면 자동으로 현재 안건을 마감하고 다음 세그먼트로 전환한다.
- **회의 종료**: 마지막 활성 세그먼트를 마감 및 요약하여 노션에 기록한 뒤 음성 채널에서 퇴장한다.

#### 세그먼트 분할 설계의 명확한 이유
1. **API 토큰 제한 극복**: Gemini API의 오디오 데이터 처리는 초당 약 32 토큰을 소모한다. 2~3시간 분량의 긴 회의를 일괄 전송하면 Gemini 무료 티어의 요청당 토큰 제한인 약 25만 TPM을 초과할 수 있다. 반면 45분 단위 세그먼트는 약 86,000 토큰에 불과해 한도 내에서 안전하게 처리가 가능하다.
2. **데이터 유실 최소화**: 녹음 도중 정전이나 네트워크 장해 등으로 봇 프로세스가 강제 종료되더라도, 이미 마감되어 노션에 업로드된 이전 세그먼트의 요약본은 안전하게 보존된다.

### 사후 관리 기능
- **회의록 재작성**: 서버 내부에 원본 MP3 파일이 보존되어 있는 기간 동안, 원하는 안건 세그먼트를 선택해 Gemini 요약을 다시 실행할 수 있다.
- **임시파일 삭제**: `tmp/` 디렉터리에 생성된 세그먼트별 녹음 데이터 폴더를 개별 혹은 전체 삭제하여 디스크 용량을 관리한다. 현재 기록 중인 세그먼트는 안전하게 보호되어 삭제 대상에서 제외된다.
- 두 기능 모두 셀렉트 콤보박스의 하단에 "메뉴로 이동" 옵션을 배치하여 뒤로가기 버튼 없이 편리하게 상위 메뉴로 회귀할 수 있도록 구현했다.

## 3. 파이프라인 심층 기술 분석

### 오디오 수집 및 변환 파이프라인
1. 사용자가 발화를 시작하면 `@discordjs/voice`의 `connection.receiver.subscribe(userId)`를 통해 Opus 패킷 스트림을 구독한다.
2. 유입된 패킷은 Node.js `stream.pipeline()` 내에서 `prism.opus.Decoder`를 거쳐 원시(raw) PCM 데이터로 디코딩된 후 로컬 파일로 순차 쓰기(Stream)를 수행한다. 이 과정에서 파이프라인이 예외로 해제되더라도 스트림 리소스가 정상 소멸되도록 안전하게 관리된다.
3. 세그먼트가 마감되는 시점(`finalizeSegment`)에 쪼개져 저장된 각 유저별 PCM 파일들을 타임스탬프 순서대로 병합한 후, FFmpeg 프로세스를 구동하여 `16kHz Mono 64kbps` 포맷의 MP3 파일로 최종 인코딩한다.
4. 특정 사용자가 발화를 진행하는 중간에 세그먼트 전환(회전)이 발생하더라도, 해당 발화 스트림은 시작된 시점의 세그먼트 폴더에 끝까지 기록되어 오디오 데이터의 온전성을 보장한다.

### Gemini API 연동 및 장애 극복 전략
기본 엔진 모델로 `gemini-flash-latest`(내부적으로 `gemini-3.5-flash`로 매핑됨) 버전을 사용한다. 특정 버전을 하드코딩할 경우 구글 측의 이전 세대 API 지원 종료 시 404 에러가 발생하므로, 항상 최신 빌드를 가리키는 Alias 식별자를 사용한다.

`gemini-3.5-flash` 모델의 무료 티어 API 호출 한도는 일일 20회로 매우 제한적이다. 이를 우회하기 위해 다음과 같은 다단계 예외 처리 메커니즘을 내장했다.

- **일일 한도 초과 대응 (Fallback)**: API 호출 결과 `RESOURCE_EXHAUSTED` 에러코드와 일일 할당량 초과(`PerDay`) 패턴이 감지되면, 호출 제한이 훨씬 유연한 하위 모델인 `gemini-flash-lite-latest`로 즉시 요청 대상을 대체하여 재시도한다.
- **일시적 서버 에러 대응 (Retry)**: 503(Service Unavailable), 500(Internal Server Error), 429(Rate Limit) 등 일시적 네트워크 및 서버 장애에 대해서는 지수 백오프(Exponential Backoff - 2초, 4초, 6초, 8초 간격)를 적용하여 최대 5회 재시도한다.
- **타임아웃 명시화**: 구글 SDK 자체에는 타임아웃 기본값이 존재하지 않아 무한 대기 현상이 발생할 수 있다. 이를 방지하기 위해 메타데이터 조회 요청 시 30초, 요약문 텍스트 생성 작업 시 최대 5분의 명시적 타임아웃을 강제 적용했다.

### Notion API 동기화 구조
Notion SDK를 통해 회의록 본문을 기록할 때, Gemini가 반환하는 마크다운 문법(`##`, `-`, `1.`, `**굵게**`)을 라인 단위로 순회 파싱한다. 파싱된 문자열은 Notion API 사양에 맞는 `heading_3`, `bulleted_list_item`, `numbered_list_item`, `paragraph` 블록 객체로 치환되며, 볼드 마크는 `bold` 어노테이션 정보로 변환되어 API 바디에 담겨 전송된다. 디스코드 고유 ID와 실명 테이블을 가진 `USER_MAP` 상수를 두어 노션 본문 내 참석자 Callout 영역에 사람이 식별할 수 있는 이름이 명시되도록 보장한다.

## 4. 트러블슈팅 및 장애 해결 기록

### 트러블슈팅 1: 디스코드 컬렉션 `flatMap` 동작 이상으로 인한 Notion 부서 필드 누락
- **문제**: 디스코드 유저들의 역할을 수집하여 Notion의 Multi-select 속성인 부서 필드에 매핑할 때, 조건에 부합하는 부서 정보가 Notion에 기입되지 않고 지속적으로 비어 있는 상태로 페이지가 생성되었다.
- **원인**: 디스코드 API의 `Collection.prototype.flatMap`은 일반 JavaScript Array의 `flatMap` 메서드와 외형은 같으나 내부 동작 메커니즘이 다르다. 디스코드 컬렉션은 Map 구조를 반환하도록 설계되어 있기 때문에, 문자열 요소를 매핑하여 반환할 경우 `[key, value]` 쌍으로 구조분해되는 현상이 야기된다. 이로 인해 '개발' 등의 2글자 문자열 중 뒷글자인 '발'만 남는 식의 데이터 오염이 일어났다.
- **해결**: 컬렉션 인스턴스를 즉시 스프레드 연산자를 사용하여 순수 배열로 강제 변환(`[...collection.values()]`)한 후, Node.js 네이티브 Array의 `flatMap` 함수를 호출하여 구조분해 문제 없이 안정적으로 부서 리스트를 배열로 결합 및 필터링할 수 있도록 수정했다.

### 트러블슈팅 2: FFmpeg 인코딩 프로세스의 비정상 종료 및 0바이트 파일 생성 현상
- **문제**: 임시 PCM 원본 스트림을 하나로 병합한 뒤 FFmpeg 프로세스를 구동하여 MP3 인코딩을 수행하였으나, 생성된 MP3 파일 용량이 항상 0바이트로 떨어지며 인코딩이 정상적으로 완결되지 않았다.
- **원인**: `@discordjs/voice`에 기본 탑재된 `prism.FFmpeg` 클래스는 인스턴스 초기화 시 전달받은 실행 인자(args) 배열의 끝단에 항상 `pipe:1` 값을 자동으로 병합하여 덧붙인다. 그러나 코드 레벨에서 인자 배열에 최종 출력 파일의 로컬 경로를 파라미터로 명시적으로 기입함에 따라 FFmpeg 엔진 내부적으로 출력 대상이 중복 지정되었고, 이로 인해 프로세스가 예외를 리포트하며 조용히 작동을 멈췄다.
- **해결**: FFmpeg의 실행 인자 배열에서 파일 출력 경로 설정을 완전히 소거했다. 그 대신 FFmpeg 프로세스의 표준 출력(stdout) 스트림을 직접 연결받은 후, `fs.createWriteStream` 인스턴스를 명시적으로 생성하여 이 스트림으로 파이프 처리하도록 로직을 재설계했다.

### 트러블슈팅 3: 디스코드 인터랙션 타임아웃 크래시 및 컴포넌트 생성 오류
- **문제**: 사용자가 회의록 재작성이나 임시파일 삭제 메뉴를 조작할 때, 봇 프로세스 내부에서 컴포넌트 빌드 도중 예외가 던져지며 크래시가 발생했다. 사용자 화면에는 봇이 즉시 대응하지 못했다는 취지의 에러 메시지만 노출되었다.
- **원인**: Discord 컴포넌트 사양상 셀렉트 메뉴의 옵션이 가지는 `value` 속성의 문자열 길이는 최대 100자로 한정되어 있다. 코드 설계 시 조작 대상인 파일의 로컬 전체 경로와 대상 Notion 페이지 ID를 온전히 조합해 `value`에 담아 보냈고, 이로 인해 100자 스펙 제한을 넘기며 API 바인딩 에러가 발생한 것이다. 이미 인터랙션은 `deferUpdate()`로 비동기 보류 처리가 진행된 직후라 봇 단독 크래시로 처리되었다.
- **해결**: 셀렉트 옵션의 `value` 영역에는 생성 타임스탬프와 같은 극히 짧은 유니크 식별자 키만 설정해 전달하도록 구성을 변경했다. 이후 디코딩 시점에는 해당 식별자를 가지고 메모리 세션 상태에서 실제 파일 경로 및 Notion API 매칭 값을 조율해 가져오도록 참조 구조를 수정했다.

### 트러블슈팅 4: Gemini File API 업로드 시 원인 불명의 404 API 에러
- **문제**: 오디오 원본 파일을 `@google/genai` 라이브러리의 `Files.upload()` 메서드를 사용해 전송하려 할 때 API 서버 측에서 404 에러를 반환하며 업로드가 원천 거부되었다.
- **원인**: 안전한 전송 제어를 위해 업로드 커넥션에 타임아웃 설정을 덧붙이고자 `Files.upload()` 함수의 실행 옵션 파라미터로 `httpOptions` 속성을 할당했다. 그러나 구글 SDK 소스 검토 결과, 업로드 메서드에 개발자가 커스텀 `httpOptions`를 직접 투입하게 되면 내부 모듈이 타임아웃 분기 처리를 하느라 업로드에 필수적인 `X-Goog-Upload-*` 형태의 세션 제어 헤더를 삽입하는 빌더 로직을 누락시키는 버그가 존재했다. 헤더 누락으로 인해 엔드포인트 수신부에서 라우팅에 실패해 404가 수신된 것이다.
- **해결**: 오디오 파일 전송 단계인 `Files.upload()` 실행 구문에서는 `httpOptions` 객체 지정을 완전히 격리 및 배제시켰다. 타임아웃은 파일 전송이 무사히 마감된 뒤 호출되는 메타데이터 대기(`get`), 실제 AI 추론 요청(`generateContent`), 리소스 폐기(`delete`) 트랜잭션 구문에만 한정 적용하는 구조로 변경했다.

## 5. 배포 환경 관련 특이사항 및 알려진 한계점

### 시스템 배포 요건
- **DAVE 종단간 암호화 규격 지원**: 이 봇은 필수적으로 `@discordjs/voice ^0.19.2` 및 Node.js 22 이상 사양을 전제한다. 디스코드가 2026년 3월을 기점으로 전체 일반 음성 채널에 종단간 암호화 표준인 DAVE 프로토콜을 강제 적용했기 때문에, 구버전의 모듈을 그대로 운용할 시 연결 직후 `4017` Close Code를 수신하며 접속이 차단된다.
- **네트워크 폴리시 제어**: 배포 호스트 환경 내부에서 Tailscale VPN과 Docker 브릿지 네트워크가 혼재되어 운용됨에 따라 `rp_filter`가 strict(1) 상태로 활성화되어 컨테이너 외부로 향하는 UDP 보이스 패킷이 모조리 차단되는 전송 장애가 있었다. 이를 해결하기 위해 컨테이너 구동 인자로 `--cap-add=NET_ADMIN` 권한을 바인딩하고, 호스트의 필터 규격을 `rp_filter=2` (loose) 모드로 완화 조정한 뒤 공용 DNS(8.8.8.8 / 1.1.1.1)를 고정 인가해 네트워크 루프를 뚫어냈다. 
- **하드웨어 및 시스템 사양**: 상시 기동을 위해 호스트 디바이스인 노트북의 하드웨어 스펙 상 `HandleLidSwitch=ignore` 처리를 수행하여 덮개를 닫아도 시스템이 대기 모드로 전입하지 않도록 조치했다. 또한 배터리 장기 보호 목적으로 하드웨어 바이오스 단에서 충전 임계치를 최대 60%로 상시 제어하고 있다.

### 잔존 한계점
1. **경계선 유실 우려**: 백그라운드 스케줄러가 작동하여 정밀한 세그먼트 자동 회전(안건 마감 및 신규 회전)이 이루어지는 수백 밀리초의 찰나의 시점에 발화된 오디오 파편의 종단 일부는 유실될 가능성이 존재한다.
2. **글로벌 다중 세션 제약**: 세션 데이터 상태가 프로세스 전역 수준에서 단일 메모리 공간에 고정 상주하도록 구현되어 있다. 여러 디스코드 길드(서버)에서 본 봇을 초대하여 동시 다발적인 회의 기록을 진행하는 시나리오는 불가능하며, 이를 보완하려면 길드 고유 ID를 키셋으로 삼아 다중 세션 인스턴스를 파티셔닝하는 별도 추상화 설계가 수반되어야 한다.
3. **민감 정보 노출**: 환경설정 파일인 `.env`에 Notion 토큰, Discord 봇 토큰 및 Gemini API 프라이빗 키 정보가 마스킹 없이 일반 텍스트 형태로 적재되어 있어, 형상 관리 저장소에 코드를 push할 경우 각별한 기밀 유지가 필요하다.
